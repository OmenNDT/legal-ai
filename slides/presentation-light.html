Thách thức & Khó khăn

Tại sao không thể tóm tắt trực tiếp?

⚠️ Giới hạn token mô hình

BART/T5 chỉ nhận ≤ 1024 token đầu vào. Hợp đồng dài nhất ~47K từ ≈ 60K token → vượt xa 60 lần giới hạn.

BART giới hạn47K từ thực tế

⚠️ Cắt cụt = Mất ngữ cảnh

Nếu chỉ lấy 1024 token đầu → bỏ lỡ điều khoản quan trọng ở cuối hợp đồng (phụ lục, bảo mật, chấm dứt).

"Hợp đồng thường đặt điều khoản quan trọng nhất ở cuối — nơi ít ai đọc."

⚠️ Tốn tài nguyên GPU

Mô hình Deep Learning xử lý văn bản dài rất tốn RAM/VRAM. Không khả thi với tài nguyên hạn chế.

VRAM 24GB RTX 3090 vẫn không đủ cho 47K token

⚠️ Không có Gold Summary

CUAD không cung cấp bản tóm tắt mẫu. Chỉ có master_clauses.csv (83 cột clause) do luật sư gán nhãn — phải tận dụng làm reference.

83 clause types → xây "tóm tắt vàng" thủ công

Bước ①

Preprocess — Từ raw text → danh sách câu sạch

📄 ContractLoader

Đọc file .txt → object Contract{'{'}doc_id, raw_text, word_count{'}'}

🧹 TextCleaner

  • Chuẩn hoá Unicode NFKC
  • Loại Page X of Y, dòng Source:
  • Gộp khoảng trắng / xuống dòng dư thừa

✂️ SentenceSplitter

  • Ưu tiên nltk.sent_tokenize (punkt)
  • Fallback regex nếu NLTK lỗi
  • Lọc câu <5 từ (tiêu đề) hoặc >80 từ (nhiễu)

🔄 Luồng xử lý

Raw: "AGREEMENT ... Page 1 of 15 ... Source: SEC filing" │ ▼ ContractLoader Contract { doc_id, raw_text, word_count: 7861 } │ ▼ TextCleaner "AGREEMENT ... " ← (đã bỏ Page/Source, chuẩn Unicode) │ ▼ SentenceSplitter List[Sentence] = [ (0, "AGREEMENT made as of...", 6), (1, "The Company shall...", 12), ... ] │ ▼ Lọc 5–80 từ List[Sentence] — chỉ giữ câu có ý nghĩa

Bước ②

Extractive — 3 thuật toán + Ensemble

Chấm điểm câu → lấy top 20% → giữ thứ tự gốc để bản tóm tắt mạch lạc

TF-IDF

Mỗi câu = 1 "document". TfidfVectorizer(ngram=(1,2)) → ma trận TF-IDF.

Công thức
score = Σ TF-IDF(câu) / |từ|

Trực giác: câu chứa nhiều từ khoá quan trọng & hiếm → điểm cao

TextRank ★ ưu tiên

Cosine similarity giữa các câu → đồ thị có trọng số → pagerank(damping=0.85)

Tương tự
PageRank của Google — câu nào được "nhiều câu vote" thì quan trọng

Thường mạnh nhất → trọng số 1.5 trong ensemble

K-Means

Embed câu bằng all-MiniLM-L6-v2 (384 chiều) → gom K cụm.

Công thức
score = 1 / (1 + dist_to_centroid)

Mỗi cụm = 1 chủ đề → lấy đại diện → tóm tắt đa chủ đề

Ensemble Min-max normalize → cộng theo trọng số
TF-IDF × 1.0 + TextRank × 1.5 + KMeans × 1.0

Bước ③

Abstractive — BART-large-CNN viết lại

📦 LongDocChunker

Nếu câu sau extractive vẫn > 1024 token → chia chunk ≤ 1024 token, overlap 50 token giữ ngữ cảnh.

🤖 BartSummarizer

  • Model: facebook/bart-large-cnn
  • Beam search: num_beams=4
  • length_penalty=2.0, no_repeat_ngram_size=3
  • Max output: 256 token → ~150–300 từ

🔄 Hierarchical

Nhiều chunk → ghép tóm tắt → nếu tổng vẫn > 1024 → tóm tắt thêm 1 vòng nữa.

Chunking & Hierarchical

[Câu extractive — 47K từ → ~9400 token] │ ▼ LongDocChunker ├── Chunk 1 (≤1024 token, overlap 50) ├── Chunk 2 (≤1024 token, overlap 50) ├── Chunk 3 ... └── Chunk N │ ▼ BartSummarizer (mỗi chunk) ├── Summary 1 (~150 từ) ├── Summary 2 (~150 từ) └── ... │ ▼ Ghép summaries Tổng > 1024 token? ├── YES → tóm tắt thêm 1 vòng (hierarchical) └── NO → bản tóm tắt cuối cùng ✅

Bước ④

Evaluate — "Tóm tắt vàng" từ CUAD + Đánh giá

🏆 ReferenceBuilder

Đọc master_clauses.csv (83 cột) → gộp các clause của từng doc (loại trùng) → "tóm tắt vàng" để chấm điểm.

Điểm độc đáo
CUAD không có gold summary → tận dụng clause labels do luật sư gán nhãn làm reference

📊 RougeEvaluator

  • ROUGE-1: unigram overlap
  • ROUGE-2: bigram overlap (fluency)
  • ROUGE-L: longest common subsequence
  • Mỗi metric: precision / recall / F1

🧠 BertScoreEvaluator

Dùng roberta-large để đánh giá nghĩa (semantic similarity), không chỉ so trùng từ vựng.

Semantic Roberta-large

📋 EvalRunner

Benchmark trên toàn bộ 510 file → lưu kết quả vào outputs/eval/rouge_*.json

POST /api/eval/run { "limit": 510, "extractor": "ensemble" }

Hạn chế & Hướng tiếp

Hạn chế hiện tại & Hướng phát triển

⚠️ Hạn chế

  • BART pretrained trên tin tức → phong cách hơi gượng với văn bản pháp lý
  • Extractive không hiểu ngữ nghĩa sâu → có thể bỏ lỡ điều khoản quan trọng nếu từ khoá hiếm
  • Chunking mất liên kết → overlap 50 token chưa đủ cho hợp đồng phức tạp
  • Reference từ clause → không phải gold summary thực sự, chỉ là proxy

🚀 Hướng tiếp

  • Thử LED / Longformer — mô hình hỗ trợ 16K+ token, xử lý trực tiếp văn bản dài
  • Pegasus-BillSum — pretrained trên văn bản pháp luật
  • Chấm điểm hậu kiểm bằng QA — dùng Question Answering để kiểm tra tóm tắt có trả lời đúng câu hỏi pháp lý không
  • Legal-specific pretraining — tiếp tục fine-tune trên corpus pháp lý lớn hơn
  • Multimodal — xử lý cả bảng biểu, sơ đồ trong hợp đồng
